# Drift Interpretation & Response Runbook

## Context

- Reference window: `data/splits/reference.parquet` (year-0 holdout, training-era distribution).
- Production window: `data/splits/production.parquet` (year-1 + synthetic perturbation from `inject_drift`).
- Reports generated by `python -m monitoring.run_monitoring`:
  - `baseline.html` (clean reference-vs-reference sanity check)
  - `drift.html` (reference-vs-production drift check)
  - `drift_summary.json` (machine-readable alert payload)
- If required DVC artifacts are missing, monitoring exits cleanly and writes a
  `drift_summary.json` payload with `"skipped": true` and missing artifact names.

## Prometheus note for batch drift metric

- `bike_feature_drift_psi` is produced in the batch monitoring process, while API `/metrics`
  exposes the API process registry.
- For project scope, treat `drift_summary.json` as the source of truth for latest drift values.
- In production, bridge batch metrics via Pushgateway or persist-and-export from a shared store.

## Why `yr`, `target`, and `prediction` can drift

- `yr` is expected to drift by design (`reference=0`, `production=1`).
- `target` and `prediction` are output-space diagnostics; they are useful but should not dominate
  the input-feature drift ratio.
- Operational alerting therefore excludes `yr`, `target`, and `prediction` from the main share
  denominator and computes an explicit `drift_share_inputs_only`.

## Current finding

- Latest summary reports alerting drift with weighted input-feature share above the configured
  threshold (`drift_threshold_share=0.20`).
- If all features were counted, share is higher (historically around ~57%).
- Input-only interpretation is the decision signal; historically this has been ~45%.

## Drift Response Workflow (Lecture 10)

1. **Investigate**: inspect `drift.html`, top drifted features, and data slices.
2. **Assess**: compare drifted features with `docs/feature_scores.json` (higher-importance features
   have higher drift weight in alerting).
3. **Decide**:
   - `P3` if below threshold: monitor only.
   - `P2` if above threshold once: investigate same day, open incident note.
   - `P2 escalation` if above threshold in 2 consecutive windows: trigger retraining.
4. **Validate**: run `dvc repro train`, compare RMSE/R² and subgroup metrics, then promote only if
   validation gate passes.

## Runbook

### Symptoms

- `drift_summary.json` has `"alert": true`.
- Prometheus `bike_feature_drift_psi{feature="<name>"}` flips to `1`.
- Input drift share exceeds 0.20.

### Mitigation

- Freeze production promotion.
- Start monitoring snapshot (`drift.html`, `baseline.html`) for incident evidence.

### Diagnosis

- Check whether drifted features are expected seasonality vs data pipeline issues.
- Prioritize high-importance features (`temp`, `atemp`, `hr`, etc.) using
  `docs/feature_scores.json`.

### Resolution

- If alert persists for 2 consecutive windows, retrain with latest data and rerun validation.
- Deploy only if test gate and subgroup metrics remain acceptable.

### Prevention

- Keep feature pipeline contracts stable.
- Track input feature quality checks upstream.
- Review threshold calibration monthly as data seasonality evolves.
